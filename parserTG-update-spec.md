# parserTG-backend — Update Spec: Multi-platform AI Editor

Статус: планирование, для реализации агентом. Всё описанное — надстройка над существующей архитектурой (Ingest → Pub/Sub → Processor → Approver → Publish), без выноса в отдельный проект.

---

## 0. Контекст

Текущий пайплайн публикует только в Telegram-канал после ручного approve через Telegram-бота. Задача: добавить публикацию в Twitter/X и Threads с AI-редактором, который пишет в едином голосе персоны, фильтрует поток новостей под дневной лимит постов, и сохраняет память о собственных прошлых постах.

Источники контента остаются прежними (Telegram-каналы через Telethon). Twitter/Threads используются **только на запись** — чтения/ingest оттуда не требуется.

---

## 1. Publisher fan-out (Twitter/X + Threads)

- После approve в Telegram-боте — параллельная публикация в Telegram / Twitter / Threads.
- Независимый статус success/fail по каждой площадке (падение одной не блокирует остальные).
- **Только официальные API**:
  - Twitter/X: `POST /2/tweets` (X API v2, pay-per-use с февраля 2026, free tier не существует).
  - Threads: Meta Graph API for Threads (`graph.threads.net`), требует Instagram Business/Creator аккаунт + Meta App Review.
- **Никакого Playwright / browser-automation** — не используем, несмотря на то что некоторые референсные репо (SocialFlow, agent-content-kit) публикуют так. Риск бана аккаунта, нарушение ToS.
- Адаптация под лимиты площадки:
  - Twitter: если текст длиннее 280 символов — оформляем как тред (несколько последовательных постов), а не обрезаем.
  - Threads: лимит 500 символов на пост, до 10 000 в text-attachment (не путать).
- Медиа (картинки/видео) — **не требуется** на первом этапе, только текст.
- Retry/rate-limit handling: при 429 или временной ошибке — ретрай с backoff, при неустранимой ошибке — алерт (см. п. 6), не блокировать остальные площадки.

---

## 2. Planner-этап (новый шаг в конвейере)

Проблема: источники дают 40+ сообщений/день, лимит постинга в Twitter/Threads — ориентировочно 4 поста/день.

- Встраивается между Processor (создание драфта) и Creator (генерация финального поста под площадку).
- LLM-скоринг: короткий вызов, оценивающий каждого кандидата по важности/релевантности персоне (шкала, например 1-10).
- Формирует **топ 5-6 кандидатов** и отправляет их в Telegram-бот со скорами/кратким обоснованием.
- **Человек (ты) выбирает вручную**, какие из топ 5-6 уходят дальше в генерацию поста — это не полностью автоматический отбор.
- Telegram-канал (основной, уже работающий) продолжает публиковаться как сейчас, **без** этого фильтра — Planner нужен только для ветки Twitter/Threads.

---

## 3. Персона AI-редактора

Полноценная личность, ведущая Twitter/Threads от одного лица, а не пост-в-пост промпт-редактирование.

- **Одна личность**, стиль адаптируется под площадку: короче/резче под Twitter, свободнее под Threads.
- Структура конфига — по паттерну проекта QwenPaw, три отдельных markdown-файла (хранятся в репо как конфиг, не зашиты в код, правки без деплоя):
  - `SOUL.md` — ценности, характер, границы (что персона никогда не делает/не говорит).
  - `PROFILE.md` — идентичность: имя, бэкграунд, вайб (даже если бэкграунд не озвучивается прямо в постах, он определяет угол зрения).
  - `AGENTS.md` — поведенческие правила: как реагирует на срочные новости vs аналитику постфактум, тон по площадкам.
- **Содержание персоны (тематика, конкретная позиция по новостям, тон)** — сознательно отложено, требует отдельного решения до реализации. Заглушки/дефолты не создавать без явного ввода.
- Reviewer-роль отдельным AI-агентом не нужна — её функцию выполняет approve-flow с человеком (см. п. 5). Analyst-роль (аналитика performance постов) — не планируется на этом этапе.

---

## 4. Контекст-слой и память

- **Web-поиск в моменте генерации** (tool use) — модель сама подтягивает фон/связанные события под конкретную новость, без отдельной базы знаний на v1.
- **Память по прошлым постам персоны** — full RAG, не просто выборка по времени:
  - Хранилище: **Firestore + Vector Search extension** (нативная функция Firestore, `find_nearest()` для similarity search).
  - Причина выбора: минимальная новая инфраструктура — используется та же БД, что уже в проекте под драфты/оффсеты, вместо отдельного ChromaDB/pgvector/AlloyDB.
  - Embeddings — отдельный вызов (OpenRouter completions их не считает): OpenAI embeddings API либо Vertex AI Embeddings.
  - Новая коллекция, например `persona_posts`: текст поста, площадка, дата, embedding-вектор, теги/тема, ссылка на исходное событие.
  - При генерации — semantic search по этой коллекции, чтобы не повторяться и связывать похожие события.

## 5. Style-pass (анти-AI-паттерны)

- Взять содержимое `SKILL.md` из репозитория `blader/humanizer` (33 паттерна AI-письма с примерами before/after: канцелярит, тире, дежурные концовки, эмодзи-заголовки и т.д.).
- **Не подключать как внешнюю agent-skill зависимость** — формат `npx skills add` не работает на Cloud Run (там нет концепции agent skills, только прямые API-вызовы к LLM).
- Вместо этого: скопировать инструкции/паттерны как часть system prompt на финальном rewrite-шаге в processor/creator-сервисе.
- Дополнительно — идея вариативности формулировок (аналог `StyleVariator` из репозитория `human-persona`, без их фреймворка): избегать одинаковой структуры фраз от поста к посту.

---

## 6. LLM-провайдер

- Переход с прямого OpenAI API на **OpenRouter** — гибкий выбор модели без переписывания интеграции (OpenAI-совместимый формат запроса).
- В Secret Manager: `OPENAI_API_KEY` → `OPENROUTER_API_KEY` (можно держать оба, если что-то по-прежнему завязано на прямой OpenAI).
- В конфиге: `GPT_PROFILE`/`GPT_INSTRUCTIONS_JSON` остаются как есть, добавляется возможность указывать модель на профиль.
- Embeddings — отдельный провайдер (см. п. 4), OpenRouter completions embeddings не считает.

---

## 7. Approve-flow (расширение существующего)

- Существующий approve/reject/redraft через Telegram-бота остаётся основным механизмом контроля — без замены на автономный постинг.
- Добавляется:
  - Список топ 5-6 кандидатов от Planner (см. п. 2) с ручным выбором, что уходит в генерацию.
  - В превью финального поста — контекст "на основе чего"/"с чем связано" (что использовано из web-поиска и памяти), чтобы видно было логику связки перед апрувом.

---

## 8. Мониторинг

- Алерты в Telegram-админ-чат (тот же, что уже используется для approve) при фейле Publisher на конкретной площадке — не блокирующие остальные площадки, но видимые.

---

## 9. Тестовое окружение

- Dry-run режим для Publisher и Planner перед деплоем в прод — чтобы не постить тестовые сообщения в реальные каналы/аккаунты.

## 10. Ориентировочный бюджет (для планирования, не жёсткий бюджет)

| Статья | Оценка/мес | Комментарий |
|---|---|---|
| Twitter/X API | $1-3 | pay-per-use, ~120 постов/мес без ссылок в тексте (~$0.015/пост); с ссылками — дороже (~$0.20/пост) |
| Threads API | $0 | официально бесплатно, лимит 250 постов/24ч, единственная цена — время на Meta App Review |
| LLM (OpenRouter, эффективные модели: Haiku/GPT-4o-mini/Gemini Flash уровня) | $1-3 | ~240-480 вызовов/мес (генерация + style-pass) при ~3-5k токенов на вызов |
| Embeddings | <$1 | малый объём постов |
| GCP-инфраструктура (Cloud Run, Firestore, Pub/Sub, Scheduler) | в рамках текущей | новых типов ресурсов не добавляется |

Twitter API-модель нестабильна (менялась дважды за 2026 год) — перепроверять актуальные ставки в Developer Console перед запуском.

## 11. Референсы: что взято, что нет

**Взято (концепция/структура, не код):**
- **QwenPaw** — структура персоны SOUL.md/PROFILE.md/AGENTS.md.
- **SocialFlow** — подтверждение ролевой схемы конвейера (Scout→Planner→Creator→Publisher как логические этапы, не отдельные сервисы/агенты).
- **human-persona** — идея вариативности формулировок (без их фреймворка).
- **blader/humanizer** — 33 паттерна анти-AI-письма, встроить в system prompt.

**Не берём:**
- SocialFlow — метод публикации через Playwright (browser automation) — нарушение ToS, риск бана. У нас только официальные API.
- agent-content-kit — видеопайплайн, публикация браузерной автоматизацией без OAuth — не подходит.
- being — требует внешний хостинг (Supabase/Ruddia), лишняя инфраструктурная зависимость.
- persona-knowledge — тяжёлая инфраструктура под fine-tuning персоны на личных архивах, избыточно для промпт-based подхода.
- role-persona — память для AI coding-агентов (Cursor/Claude Code), другой use case.
- chronicler — self-hosted RP-чат клиент, интерактивная память для диалогов, не для автономной генерации постов.
- thefeed — DNS-based обход цензуры + мессенджер, не релевантно задаче вообще.

## Открытые вопросы (требуют решения до/во время реализации)

1. **Содержание персоны** — тематика, конкретная позиция по новостям (нейтральная/с мнением), тон — не определено.
2. Дедупликация контента между площадками — сейчас предполагается, что разная подача под разную аудиторию площадок это нормально, разное решение не требуется.
